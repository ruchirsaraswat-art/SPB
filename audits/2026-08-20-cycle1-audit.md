# Domain audit: analog-spec-tool (2026-08-20, overnight cycle 1)
Auditor: Circuit_Researcher agent. Scope: `backend/topologies.py`, `backend/main.py`, `backend/circuit_researcher.py`, `frontend/src/SpecForm.jsx`, `frontend/src/phyArchitectures.js` (topology mapping only).

Overall verdict: the per-topology field sets, units, and help text (implemented after the previous audit) are correct and well-worded — the embedded numbers (TIA 0.7x-bit-rate bandwidth rule, PLL loop BW = ref/10–ref/20, aperture-jitter SNR formula, CML swing 0.8–1.2 Vpp, 0.3–0.4 UI edge rates) were re-checked and no unit or formula errors found. All `topology:` values referenced by the PHY diagrams exist in the catalog. The problems that remain are missing cross-cutting fields, absent validation/feasibility bounds, and a few concrete correctness bugs below.

## P1 — correctness (tool currently shows/accepts wrong info)

**1. Current-mirror form accepts DRC-illegal device widths (min W = 0.15 µm).**
- WHAT: In `SpecForm.jsx`, "Reference device width W" has `min="0.15"`. sky130's minimum gate *width* for custom layout is **0.42 µm** (0.36 µm is allowed only inside standard cells, 0.15 µm only inside SRAM macros). Only gate *length* may go down to 0.15 µm. The models will happily simulate 0.15 µm width, so nothing downstream catches it — the user gets a "successful" design that cannot pass DRC.
- FIX: Set width input `min="0.42"` and add help text ("sky130 custom-layout minimum gate width; 0.15 µm applies to length only"). In `main.py`'s `RunSpec` validator, require `w_ref_um >= 0.42` and `l_ref_um >= 0.15`, and also check the *derived* mirror width `w_ref_um * ratio_out / ratio_ref >= 0.42` (a 1:4 ratio with W_ref = 0.5 µm currently yields an illegal 0.125 µm output device).

**2. Example specs in the UI/docstrings are far beyond what sky130 can do.**
- WHAT: The notes placeholder in `SpecForm.jsx` says "e.g. 25 Gb/s NRZ, 5m copper channel"; `main.py`'s `ResearchSpec` docstring example is a 10 GHz PLL output. sky130 peak device fT/fmax is ~63/121 GHz, but real circuit speeds are far below peak-device numbers: published open-source sky130 SerDes work is ~1–2 Gb/s class and PLL/VCO work clusters at or below a few GHz. 25 Gb/s NRZ (12.5 GHz Nyquist) is not credible; a user copying the placeholder gets a doomed run and misleading calibration of what the tool can do.
- FIX: Change the placeholder to something achievable, e.g. "e.g. 2.5 Gb/s NRZ, single-ended input"; change the docstring example to a 2.5 GHz output PLL. Pair with the soft feasibility warnings in item 5.

## P2 — important gaps

**3. No temperature field anywhere.**
- WHAT: The spec has a process corner but no temperature; ngspice defaults to 27 °C. Two concrete consequences: (a) the bandgap's headline spec `temp_coefficient_ppm_per_c` is *unmeasurable* without a temperature sweep — the tool asks for a number Circuit_Builder cannot verify; (b) worst-case speed is really ss + 125 °C + low Vdd, so an "ss corner" run at 27 °C understates the slow case.
- FIX: Add `temp_c` (number, default 27, range -40…150) to `RunSpec`/`ResearchSpec` and the form's common fields, and pass it into both prompt builders (a `.temp` line in the testbench). For `bandgap_reference` specifically, instruct the builder (in `circuit_builder.py`'s generic branch, keyed on topology) to run a DC temperature sweep across `temp_range_c` and report measured ppm/°C.

**4. No load-capacitance field for voltage-output blocks.**
- WHAT: Bandwidth, delay, and jitter specs are meaningless without the load: comparator propagation delay, clock-buffer additive jitter and duty-cycle, CTLE/VGA bandwidth, sense-amp regeneration, and sampler droop all scale directly with load capacitance. Right now Circuit_Builder must invent a load, and the "measured vs target" comparison is against an unstated condition. (Only `output_driver`/`input_termination_buffer` are fine — their load is the termination impedance.)
- FIX: Add `cload_ff` ("Load capacitance", unit fF, help: "Capacitance each output drives; typical on-chip 5–50 fF — delay/bandwidth specs are meaningless without it") to `ctle`, `vga`, `comparator`, `sense_amp_slicer`, `sampler`, and `clock_buffer_distribution` (label it "per-load capacitance" there, alongside `fanout_loads`) in `TOPOLOGY_FIELDS`.

**5. No plausibility bounds on any spec field — nonsense values sail through.**
- WHAT: `extra_fields` is `dict[str, Any]` with no range checks: negative data rates, 500 % duty cycle, 200° phase margin, 300 dB PSRR are all accepted and forwarded verbatim to expensive agent runs. There is also no sky130 feasibility layer at all (the "feasibility hints" this file is supposed to carry don't exist yet).
- FIX: Extend each `TOPOLOGY_FIELDS` entry with optional `min`/`max` (hard, physical validity) and `warn_above`/`warn_below` (+`warn_text`, soft sky130 feasibility). Enforce hard bounds in a `RunSpec`/`ResearchSpec` validator; render `min`/`max` on the `<input>` and show `warn_text` inline in `SpecForm.jsx` without blocking submit. Concrete starting values: `phase_margin_deg` 20–85, warn <45; `duty_cycle_pct` 30–70; any `data_rate_gbps`/`serial_data_rate_gbps` >0, warn above 5 ("aggressive for sky130; >10 unrealistic"); `output_freq_ghz`/`clock_freq_ghz` warn above 4; `temp_coefficient_ppm_per_c` warn below 10 ("needs trimming/curvature correction"); `psrr_db` warn above 90; `peaking_db` warn above 12 ("more than one CTLE stage needed"); `output_swing_vpp` warn above `vdd_v` (needs the supply value — do this check in the backend validator).

**6. `extra_fields` keys are never validated — typos are silently discarded.**
- WHAT: `extra_fields_target_dict()`/`format_extra_field_lines()` only read keys defined for the topology; any unknown key (typo, stale client, wrong-topology leftover) vanishes with no error. A user's spec constraint can be silently ignored.
- FIX: In the shared model validator, reject keys not present in `topology_fields(self.topology)` with a clear message listing valid keys. (The frontend already clears `extra_fields` on topology change, so this only bites API/CLI users — exactly the ones with no other guardrail.)

**7. `vdd_v` unconstrained; 1.8V-device assumption never checked.**
- WHAT: `vdd_v` is only `gt=0`. Entering 3.3 V or 0.6 V is accepted, but Circuit_Builder's prompts and the help text assume `*_01v8` devices (rated 1.8 V nominal, usable ~1.2–1.98 V). At 3.3 V the design would overstress every device; below ~1.2 V the high pfet_01v8 |Vt| (~0.6–0.9 V depending on flavor) makes most topologies infeasible without lvt devices.
- FIX: In the validator: error (or hard warning routed into the prompt) if `vdd_v > 1.98` telling the user the 5V family (`nfet_g5v0d10v5`/`pfet_g5v0d10v5`) is required and must be stated; soft warning if `vdd_v < 1.2` ("headroom: sky130 pfet Vt is high; expect lvt devices / reduced stacking"). Mirror the warning in the form.

**8. Corner list omits the skewed corners sf/fs.**
- WHAT: `corner: Literal["tt","ff","ss"]`. The local `sky130.lib.spice` also provides `sf` and `fs` (verified), and for the blocks this tool builds most — comparators, sense amps, CML stages, clock buffers — the *skewed* corners (fast-N/slow-P and vice versa) are the worst case for offset, N/P symmetry, and duty-cycle distortion, not ss/ff.
- FIX: Extend the Literal and the dropdown to `tt/ff/ss/sf/fs`; update `FIXED_HELP.corner`: "ss is worst for speed; sf/fs (skewed N vs P) are worst for offset/symmetry specs like comparator threshold and duty cycle."

**9. PLL field set has no jitter spec.**
- WHAT: `pll` asks for ref freq, output freq, loop BW, and phase margin — but loop BW and PM are *design parameters*, while integrated jitter is the deliverable a PLL is actually specified by. A user cannot currently express "I need <2 ps rms" except in free-text notes.
- FIX: Add `rms_jitter_ps` ("Integrated rms jitter", unit ps, help: "RMS jitter of the output clock integrated over the band of interest — the PLL's headline deliverable; loop bandwidth/phase margin are means to hit it") to `pll`, and optionally `recovered_clock_jitter_ps` to `cdr`.

**10. Catalog gaps: no op-amp/OTA, no LDO, no DLL/phase interpolator.**
- WHAT: (a) The general-purpose OTA/op-amp — the most common analog block, and a building block *inside* the bandgap and any LDO — is absent (this user also actively does amplifier interview prep, so it's squarely in their workflow). (b) Every PHY diagram has a Vref generator but no regulator, though clean regulated supplies are how real PHYs power VCOs/clock paths. (c) The DDR/LPDDR diagrams map all clocking to `pll`, but DDR PHY clocking is conventionally DLL/phase-interpolator based (per-lane deskew, 90° shifts).
- FIX: Add three entries to `TOPOLOGY_GROUPS`/`TOPOLOGY_FIELDS`: `opamp_ota` (fields: `dc_gain_db`, `gbw_mhz`, `phase_margin_deg` warn <45, `cload_pf`, `output_swing_vpp`, `input_referred_noise_nv_per_rthz`); `ldo` (fields: `output_voltage_v`, `max_load_current_ma`, `dropout_mv`, `psrr_db_at_1khz`, `load_cap_uf_or_capless` text); `dll_phase_interpolator` (fields: `clock_freq_ghz`, `num_phases`, `phase_step_ps`, `integral_nonlinearity_lsb`). Optionally remap the DDR/LPDDR clocking blocks in `phyArchitectures.js` to the new DLL entry.

## P3 — nice to have

**11. Serializer/deserializer accept inconsistent rate/width/clock triples.**
- WHAT: `parallel_clock_freq_mhz` is by definition `serial_data_rate_gbps * 1000 / parallel_width_bits`, but it's an independent input — a user can enter 32:1 at 2 Gb/s with a 100 MHz word clock (should be 62.5 MHz) and nothing objects.
- FIX: Either auto-compute the field in the frontend (read-only derived display) or add a backend cross-check that warns when the entered value deviates >1 % from the derived one.

**12. Return-loss sign convention is ambiguous.**
- WHAT: `input_termination_buffer.return_loss_db` help says "-10 dB or better" while the field is labeled "Return loss", conventionally a *positive* dB number (RL = 10 dB means S11 = -10 dB). Users will enter mixed signs and Circuit_Builder can't tell -10 from 10.
- FIX: Reword label/help to "Return loss (enter positive dB, e.g. 10 = |S11| of -10 dB); larger is better" and set `min: 0`.
